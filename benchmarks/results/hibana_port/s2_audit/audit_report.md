# Hibana 移植 S2 審查意見(budget 4:48:5,DeepSeek-V4.1-Flash,TP=2)

**總評**

- **S1 審查提出的修正大多已落實。** 包括 ucount 對帳、實測斜率、grid 語義、soft cap、不改名、store_y=0、TP 一致性檢查,以及 off-path sha 一致。
- **C8 +6.26% 作為「速度有變化」的證據是可信的,足以進入品質階段。** 但它還不足以證明「同品質下更快」:C8 下的輸出長度、內容和 MTP 接受率都沒有量。
- **單流「雜訊」的說法需要修正。** 數據顯示的是 ABAB 設計下的線性漂移,不是零效應的直接證據。
- **核心本身的離線驗證很扎實,但沒有覆蓋整合層。** 至少有 4 個整合風險需要在 S3 前關閉。

標記說明:【計算】是我用 dossier 數字算出的;【推論】是我的推斷;【建議值】是我提出、需預先登記的門檻;其餘皆為 dossier 原文數字。

## (1) 量測方法與數據盲點

**A. C8 效果量大,但統計單位要說清楚。**

- 以 4 vs 4 樣本計:差 9.9 tok/s,Welch t ≈ 11.5;完全分離的排列檢定 p = 2/70 ≈ 0.029【計算】。
- 但每個 arm 內的 rep 0 和 rep 1 共用同一次啟動,不是獨立重複。真正的獨立單位是「重啟」,每臂 n = 2。
  - 2 vs 2 的排列檢定,最小 p 只能到 0.33【計算】。設計本身無法給出形式顯著性。
- 支撐結論的是效果量:B 的最小值 166.9 比 A 的最大值 159.1 高 7.8 tok/s,約為合併 sd 的 6 倍【計算】。
- 結論:速度差異可信,但目前的檢定力來自效果量,不是來自設計。

**B. ABAB 不能抵消線性漂移,單流數據正好顯示了這一點。**

- 單流 greedy 依執行順序單調下降:A1 87.88 → B1 87.47 → A2 87.32 → B2 86.97。
- 我逐題計算了 9 個 prompt 的 A、B 平均:**9/9 題都是 B 較低**,平均約 −0.35 tok/s(−0.4%)【計算】。若當作獨立檢定,符號檢定 p ≈ 0.004。
- 不過 ABAB 下 B 平均晚一個位置,而每一步的漂移約 0.28–0.30 tok/s(A1→A2 降 0.56,B1→B2 降 0.50)【計算】。
  - 所以這個差異幾乎完全可以用漂移解釋【推論】。
- 這帶出三點:
  1. dossier 稱「noise」並不精確。正確說法是「與線性漂移一致,無法與 R≥5 時多出的 kernel launch 開銷區分」。
  2. 在 C8,漂移方向對 B 不利,所以 +6.26% 偏保守【推論】。
  3. **之後所有 A/B 改用 ABBA 或 ABBAAB。**

**C. C8 吞吐提升的歸因沒有被驗證。主要殘餘混淆如下。**

1. **輸出內容與長度改變。**
   - budget 生效時 C8 輸出會偏離基線。agg tok/s 等於「生成 token 數 / 牆鐘時間」。
   - 若 B 更早 EOS、尾段少於 5 流的時間比例改變,或出現重複迴圈,都會改變 agg。
   - 迴圈還會**提高** MTP 接受率,進而提高吞吐【推論】。
   - dossier 沒有列出 C8 每流的 token 數、接受與 draft 計數,也沒有 sha 或長度比較。這是目前最大的混淆。
2. **MTP 接受率(C8)未量。** 速度收益是「回合變短」與「每回合 token 數變化」的淨值,目前無法拆分。
3. **adaptive draft depth 依計時調整。**
   - 單流 drafted 數在不同 arm 間有 ±1 的波動(例如 381 對 382,372 對 373),證明它對時序敏感。
   - budget 讓回合變短後,C8 的 draft depth 分布可能改變。這屬於合法效果的一部分,但需要報告。
4. **沒有生效計數器。**
   - 不知道 C8 中有多少比例的 verify 回合真的觸發 budget,也不知道觸發後 ucount 的分布。
   - soft cap 下,keep 集合聯集本身就可能 > 48;16 列 × keep 4 最多 64 個 expert【推論】。

**D. 與預測的對比需要更正算術。**

- 回合時間減少 7.5%,在每回合 token 數不變時,對應吞吐上升 1/(1−0.075) − 1 ≈ +8.1%,不是 7.5%【計算】。
- 觀測到的 +6.26% 吞吐,等價於回合時間減少約 5.9%【計算】,約為上界的 77%。
- 不是所有 C8 回合都是 16 列,也不是都觸發 cap,所以接近上界有兩種解釋【推論】:
  - 接受率沒有明顯下降;
  - 或混淆 1(輸出變化)在起作用。
- 建議在 B arm 開 TF_DS_EXPERT_STATS=3 跑一次 C8,直接驗證機制。預期:
  - 16 列回合的 ucount 從約 52 降到 49 左右(含 shared);
  - 每層時間按斜率 28.6 µs × Δu 下降。

**E. 其他盲點。**

- C2、C4 雖未觸發 cap,但 R ≥ 5 的回合仍會 launch kernel,只是提前返回。這部分開銷沒有單獨量測。
  - C4 的 B − A 為 −0.27%,在雜訊內。
- 單流在 R ≥ 5 時也會 launch。開銷上界為 40 × 6–10 µs ≈ 0.24–0.4 ms/回合【計算】。
- 生產流量中 ≥5 streams 的時間占比仍未提供。這決定整體收益,是 S1 就提過的盲點。

## (2) 可成立結論與過度推論

**可成立:**

1. 在本測試工作負載的 C8 下,budget 4:48:5 帶來可重現的吞吐提升,約 +6%,4/4 分離。
2. 1 到 4 streams 完全不受影響:
   - 單流 4 arm 的 token sha 與生產一致;
   - C2/C4 在雜訊內。
   - 這同時證明 off-path 與門控在這些負載下正確。
3. 核心邏輯與獨立 C++ 參考實作位元一致(57,240 次呼叫、6 組配置)。no-op 配置確實不改寫任何資料。
4. 成本模型(28.6 µs/expert/layer,約 1.14 ms/回合/expert)與觀測量級一致。S1 擔心的 wave 階梯在 u = 27..69 範圍內沒有出現。

**過度推論或尚不成立:**

1. **「+6.26% 是同品質下的加速」不成立。** C8 輸出、長度、接受率都未比較(見 1C)。
2. **「單流差異是雜訊」應改為「與漂移一致」。** 見 1B。
3. **離線 57,240 次呼叫的零誤差,只驗證了 kernel 函數本身。**
   - 它沒有驗證整合層的輸入,特別是 `row_slot` 指標(見第 3 節 R1)。
   - replay 用的是 host 端擷取的 `rows.slots`,不是 kernel 實際讀到的 device 緩衝。
4. **「C8 有效」不能外推到生產混合流量。**
   - 本測試的 C8 多為同領域的 code prompt,聯集較小。
   - 跨領域批次的聯集更大,觸發更頻繁、丟棄更多,速度收益和品質損失都可能更大【推論】。
5. **新的系統性問題:對少數派請求的公平性。**
   - 填充規則是「按全批 routing weight 總和」,會偏向多數 stream 共用的 expert。
   - 結果是:一個中文或數學請求和 7 個 code 請求同批時,它的第 5、6 個 expert 被丟的機率顯著較高【推論】。
   - 同質批次的品質評測會**低估**這類請求受到的傷害。
6. **批次不變性喪失仍需產品端決策。** 速度數據無法替代這個決策。

## (3) 下一階段是否值得做與具體參數

**結論:值得做 S3,但有前提。**

- 先關閉以下整合風險,約 1–2 小時工程,不占 GPU 預算。
- 同時取得生產 streams 分布。若 ≥5 streams 的 token 占比很低(例如 < 20%【建議值】),整體收益不到 1.3%。這種情況下不值得以批次不變性為代價,應直接結案。

### 3.1 必須先關閉的正確性與整合風險

**R1:`row_slot = rd.inputs + 2*R*8` 的 stride 假設。**
- 這個寫法假設 inputs 是 [3][R]、stride 為 R。若實際 stride 是 max_rows 或 graph bucket,kernel 會讀到錯誤資料,stream 計數也會錯。
- 離線 replay 無法發現這個問題。
- 處理:加 debug 模式,把 kernel 讀到的 row_slot 拷回,逐回合與 host 的 `rows.slots` 比對。

**R2:padding 列與非 verify 列。**
- 若 graph bucket 會補 padding 列,或 verify 回合可能夾帶 prompt chunk 或其他非 verify 列,問題有兩個:
  - 它們的 slot 值會被算成一個 stream。例如 4 流加上哨兵值 −1,就成為 5 流,C4 也會觸發。
  - 它們的 picks 會進入聯集與 score,影響真實列的選擇。
- `moe()` 的程式碼本身沒有 verify 與 prompt 的判斷,「只作用於 verify 回合」目前只是 dossier 的陳述。
- 處理:讀碼確認,並用計數器證明 C4 觸發次數為 0。

**R3:2D 路徑(world 4,`e.two`)未接上 `routed_only_y`。**
- diff 只改了 `exl3_experts.decodeLaunches`。在 TP4/2D 下開啟 budget 會出問題:
  - pick −1 的 slot 會走 store_y=1 的舊行為,0 × 殘值 y 可能產生 NaN;
  - 計數器語義也未知。
- 處理:在 `e.two != null` 時,載入階段直接 `return error.BadMoeBudget`。

**R4:`min_streams` 預設為 "1",且接受 0。**
- 例如 `TF_DS_MOE_BUDGET=4:48` 會在單流時生效(單流 R ≥ 9 時聯集就可能 > 48)。
- 處理:改為必填,且要求 ≥ 2,或強制 ≥ 5。

**R5:「keep = 前 4 個 slot」依賴 `_route` 按 (sc+bias) 降序寫出。**
- 若 topk 是 unsorted,或順序並非降序,keep 的語義就錯了。C++ 參考採用相同定義,所以無法發現。
- 另外,bias 排序與 weight 排序不同。被丟的 slot 可能權重很大,導致 f = all/kept 放大。
- 處理:
  - 讀碼並斷言排序;
  - 增加計數器記錄 max f 及其分布。

**R6:`rd.pick` / `rd.mw` 的其他消費者是否容忍 −1?**
- 需要逐一確認:prefetch、統計、drafter 輸入、任何以 pick 為索引的路徑。

**R7(低風險,屬於脆弱寫法):**
- 排名迴圈中,`present[e]` 在其他執行緒讀取時被寫成 2。因為只檢查真假值,所以目前正確。但這是資料競爭,建議改寫到獨立的 `rank_ok[]`。
- R > 64、slots > 8、E > 512 時會靜默不生效。應在載入時斷言 `max_rows ≤ 64`,避免日後擴大 max_rows 時 budget 悄悄失效。

**R8:缺少生效統計(S3 判讀的必要條件)。**
- 需要 device 計數器記錄:
  - 觸發回合數;
  - 觸發前後的 ucount;
  - 每列被丟的 routed weight 比例;
  - 按 stream 區分的最大值。
- 沒有這些,S3 無法區分「品質沒變」與「根本沒觸發」。

### 3.2 S3 品質閘門(約 3 小時 GPU)

**原則一:強制觸發。**
- 每一輪都要讓 ≥5 個**不同** prompt 同時活著:用封閉迴路 C8 加待處理佇列。
- **不能把同一題複製 8 份。** greedy 下 8 個相同 stream 的路由完全相同,聯集等於單流聯集,cap 根本不會綁住。
- 每一輪都要記錄觸發率(R8),作為測試有效性的前提。

**原則二:利用基線的批次不變性。**
- 先驗證基線 A 在 C8 下的 greedy 輸出與單流 sha 一致。
- 若一致,則在 budget 下第一個分歧 token 之前,B 的每個 token 都是在基線前綴上做 teacher-forced 預測。
- 因此可以用「首次分歧位置」估計**每 token top-1 翻轉率**:翻轉率 = 分歧數 / 分歧前累計 token 數,屬於設限存活分析。
- 這是在沒有 logits API 的情況下,最接近 teacher forcing、統計力也最高的指標。

**原則三:加陽性對照。**
- 跑短版的 4:32:5。S1 模擬顯示它丟棄 11.1% 權重、影響 73% rows。
- 若各指標連 cap 32 都分不出來,說明閘門不靈敏,4:48:5 的「通過」沒有意義。

**時間分配(以 C8 約 160 tok/s 估算【計算】),全部採 ABBA:**

| 階段 | 時長 | 內容 | 量測 |
|---|---|---|---|
| T0 | 15 分 | 關閉 R1–R8;C8 基線不變性檢查(16 個 prompt) | sha;觸發率;C4 觸發 = 0 |
| T1 | 35 分 | 64 個不同 prompt(9 code + 30 題庫 + 25 個跨領域:中文、數學、工具、長 thinking),512 token,greedy,3 種排列(改變同批鄰居),arm A/B;4:32:5 只跑 1 種排列 | 翻轉率;分歧比例;/metrics 接受率差;長度與 EOS 分布;n-gram 重複率 |
| T2 | 約 100 分 | 正確率配對 A/B:從 run_full_eval / run_omni_eval 取 ≥300 題可自動評分題目(含 ≥30 題長推理,4–8k token),C8 並發、題目隨機混排(混合領域) | 逐題配對,McNemar 精確檢定 |
| T3 | 30 分 | C8 下的 loop probe;「少數派」批次:1 個中文或數學 stream + 7 個 code stream,重複 8 次輪替 | 迴圈數;少數派 stream 的翻轉率 / 丟棄權重 vs 多數派 |

**T2 的可行性與檢定力:**
- 300 題 × 約 1.5k token × 2 arm ≈ 0.9M token,約 95 分鐘【計算】。
- 若 A 已驗證批次不變,A arm 可重用單流或既有的 temp-0 結果,省下約一半時間。這是條件式節省。
- 若題庫可用題數 < 300【推論:dossier 未提供 run_full_eval 的題量】,降級為「只能偵測 ≥8 點的退化」,並明確寫進結論。

**統計力限制的處理(必須誠實寫進決策紀錄):**
- 配對二元結果、不一致率約 15%、單側 α = 0.05、power 0.8 時【計算】:
  - 偵測 5 點退化約需 370 題;
  - 偵測 3 點約需 1,030 題。
- 3 小時內**只能排除 ≥5 點左右的退化**,也就是 Hibana keep 4 那種量級(−6.6)。無法排除 1–3 點。
- 這個缺口的補償方式:
  - 以 T1 翻轉率(高統計力)作為主判定,T2 作為「排除大型傷害」的檢查;
  - 用劑量反應(cap 32 > cap 48)驗證指標方向;
  - 若最終上線,**以 opt-in 或限定負載的方式**,而非全域預設。
- 不要用 temp > 0 的多種子來「增加 n」。題目才是聚類單位,有效 n 仍然是題數。

### 3.3 參數

- **主測:4:48:5**,與 S2 相同,保持速度數據可對照。
- **陽性對照:4:32:5**,只跑 T1 一個排列。
- **備援:5:48:5 或 4:56:5。** 只在 4:48:5 因翻轉率或接受率失敗、但幅度接近門檻時,才補跑 T1 + 速度,不重跑 T2。
- **不建議調低 min_streams。** 收益只存在於 ≥5 流,4 流以下維持位元一致。

## (4) 驗收門檻與回退條件(皆為【建議值】,須在跑 S3 前登記)

**有效性前提(不滿足就判定測試無效,不是通過):**
- C8 穩態的 verify 回合觸發率 ≥ 50%,且觸發後的 ucount 分布與 S2 一致。
- 基線 A 在 C8 下與單流 sha 一致。若不一致,改以 A 對 A 的翻轉率作為雜訊底線,再做差值。
- 陽性對照 4:32:5 的翻轉率需明顯高於 4:48:5,約 ≥1.5 倍。

**品質(全部須通過):**
1. **翻轉率(T1):**
   - 每 token top-1 翻轉率 ≤ 0.5%,等同中位分歧位置約 ≥ 140 token【計算】;
   - 少數派 stream 的翻轉率 ≤ 多數派的 2 倍。
2. **MTP 接受率(C8,/metrics 差值):**
   - B − A ≥ −0.010;
   - 且下降幅度不超過 A 對 A 執行間差異的 3 倍。
3. **正確率(T2):**
   - 配對差的單側 95% 下界 > −5 點,點估計 ≥ −2 點;
   - 長推理子集不得有方向性退化(該子集為描述性報告,不做檢定)。
4. **行為:**
   - loop probe 零新增迴圈;
   - C8 平均輸出長度變化在 ±5% 以內;
   - EOS 與截斷比例變化在 ±3 點以內;
   - 30 題 ≥ 28/30(只作煙霧測試)。
5. **穩定性:**
   - 零 NaN、零 hang、零缺列輸出;
   - 1 小時 C8 marathon(不計入 3 小時預算,通過前 4 項後再跑)零異常。

**速度(重新確認):**
- ABBA,每臂 ≥ 3 次重啟。
- C8 agg ≥ +4%,且大於 2 倍重啟間 sd。
- **同時報告 C8 每流 token 數與接受率,證明提升不是來自輸出變短或迴圈。**
- 單流、C2、C4 在漂移校正後差異 ≤ 0.5%。
- 單獨報告 kernel launch 的提前返回開銷。

**回退條件(任一成立即回退):**
- R1–R6 任一項無法以讀碼加測試關閉。
- 生產 ≥5 streams 的 token 占比 < 20%,或產品端不接受「輸出依同批流量而變」以及少數派受損的公平性問題。
- 任一品質門檻失敗,或有效性前提不成立而又無法在預算內補救。
- 速度重測後 C8 提升 < 3%,或可由輸出長度或迴圈解釋。
- 任何 NaN、hang、計數器卡死。

**回退方式:**
- 未採納時,移除 budget kernel 與 `routed_only_y` 分支,不要只是預設關閉 env。
- 量測掛鉤(含寫死的 `/home/...` 路徑)移到獨立的 debug build。
- 採納時:
  - 預設仍為關閉,以明確的 env 或部署配置啟用;
  - 每次發版都以 env off 重新驗證 9 題 greedy sha 與 p17 一致;
  - 以 env on 驗證 1–4 流 sha 一致,作為門控的回歸測試。

## gpt-6-astra (ok=True, finish=stop, wall=114.7s)

## 1. 量測方法與數據盲點

**總評：C8 的約 +6.26% 是可信的局部效能訊號，足以支持一個限時 S3；但尚不足以核准上線，也不能把它解讀成原模型的無損加速。先修正核心的資料競爭，再做品質測試。**

**此次確實補上的證據：**

- 相同前 1,280 rounds 的 engine／dump 計數一致，解除了先前 47.39 與不同快照比較的疑點。
- round-level union 是此次 kernel 的工作單位，且 CUDA graph 使用上限 grid、超出 device `ucount` 的 programs 提早退出，原先的單位與 graph 疑慮已有說明。
- A/B 使用相同 binaries、關閉量測 hooks、各 arm 重啟；C8 所列樣本均為 `ext 0`。
- 四筆 A 的範圍為 156.8–159.1，四筆 B 為 166.9–169.4，沒有重疊。兩次 B 均優於鄰接的 A，不是單一離群值造成。

**但統計上不是四個完全獨立的重啟實驗。**每個設定只有兩次 restart arm，每個 arm 內再重複兩次。相同 prompt、相同進程狀態與固定 ABAB 次序使觀測相關【推論】。因此：

- +6.26% 可當本工作負載的描述性估計。
- 不宜用四筆觀測直接建立過度精確的信賴區間，更不能以 9,760 layer-calls 補強端到端效果的統計力。
- 固定次序仍混有時間漂移；重啟不保證相同的暖機、圖擷取、快取或統一記憶體狀態【推論】。下一輪應平衡 AB／BA 次序，保留每次完整執行紀錄。

**成本模型比 S1 好很多，但仍是觀察性回歸。**

`22.8 + 28.60 × ucount µs`、各 rows 斜率 26.4–29.9 µs，支持「此區域內成本大致隨 union 線性增加」。它尚未證明減少一個 expert 必然產生相同的因果節省：expert 身分、成員列數、layer、記憶體狀態仍可能共同變化【推論】。

另外：

- mode 3 沒有 dumps，但仍插入計時／統計 kernels，使用 mapped host memory，且只量 rank 0；不是零擾動測量。
- 所附時間 histogram 保留 count 與總時間，沒有逐樣本時間或時間平方和，不能由它重建 cell 內變異。
- `1.14 ms × 5.8 ≈ 6.6 ms` 是**跨 40 層平均少同樣數量 experts 的推算**，不是每輪實測節省。
- 約 7.5% 的時間下降，固定工作量下對應約 `1 / (1−0.075) − 1 ≈ 8.1%` 吞吐增加【計算】，不能直接和 +6.3% 吞吐相減。實際 round 組成與每輪產出 token 又不固定。

**最大盲點仍是 active C8 的工作量與品質。**沒有 C8 acceptance、輸出長度、每輪產出、實際觸發率與 union 減量，無法分辨收益中有多少來自少讀 experts、有多少來自生成軌跡及排程改變。現有吞吐收益已包含當次 MTP 行為的淨影響，卻不能解釋它。

A2 C4 的 `ext 1` 排除看來與摘要一致，但須公開預先訂定的排除規則；不要一邊說每格 reps 2，一邊不標記該摘要實際只剩一筆乾淨樣本。

## 2. 可成立結論與過度推論

**可以成立：**

1. `4:48:5` 在此次 C8 code-prompt 工作負載上有可重複的效能增益。
2. off-path 的九個 greedy token SHA 與 p17 相同，是有價值的相容性證據。
3. 57,240 次離線 replay 與獨立參考 bitwise 一致，支持選擇規則實作正確；但不涵蓋所有並行執行、整合及數值邊界。
4. `pick=-1` 避免了改名後增加 FFN rows 的設計問題。`store_y=0` 的整合方向正確；實際跳過 NaN／殘值與 completion counter 的分支仍須檢查完整 CUDA 原碼，所附 Zig diff 本身不能證明全部行為。

**不能成立：**

- 「單流 acceptance 不變，所以品質無損」：該處 budget 不作用。
- 「streams ok／pass，所以 C8 正確」：這些只證明既有 gate 通過，不是答案正確性。
- 「總 routing weight 保持，所以模型輸出尺度／語義保持」：保留權重和不等於保留加權 expert 向量；FP32 重算亦不保證總和 bitwise 相同。
- 「TP 配置一致，所以兩 rank 選擇一致」：還需輸入 picks、weights、row slots 一致，以及 kernel 無競爭。
- 「cap 48 是硬上限」：guaranteed union 可以超過 48。
- 「固定 seed 就可重現」：active 時輸出取決於共同排程的請求；seed 不固定批次組成。

**程式碼仍有應先修正的正確性風險：**

- **共享旗標的多寫者競爭。**多個 threads 可同時寫入同一 `present[e]=1` 或 `chosen[e]=1`，而它們是非 atomic 的 byte。寫相同值不等於沒有資料競爭；後面的 barrier 也不能消除已發生的競爭。
- **排名迴圈的讀寫競爭。**某 thread 掃描 `present[o]` 時，另一 thread 可能把同一元素從 1 改成 2。兩者在布林判斷上都為真，說明了演算法意圖，但不能據此宣告實作無競爭。建議讓每個 expert thread 自行掃描 `sp` 建立旗標，排名期間只讀旗標、另存選入結果。
- **全域狀態生命週期。**`routed_only_y` 是模組全域變數，初始化只看到設為 `true`，未看到對每次模型載入重設。此次每 arm 重啟掩蓋了同進程重新載入／多實例的風險【推論】。
- **邊界與靜默退化。**超過 `R=64`、`slots=8`、`E=512` 就直接 return；應在載入時拒絕不支援配置，不能讓「已啟用」實際靜默失效。parser 亦未拒絕多餘欄位或限制 `min_streams`。
- **範圍外整合。**budget 呼叫在 `e.two` 分支之前，但本次只展示一般 expert 路徑的 `store_y` 修改。TP=2 證據不能外推到該分支。
- `kept<=0` 時使用 `f=1`，不足以普遍保證 routed sum 保留；需明確限定有限、有效 routing weights 的輸入契約，補測極端權重與非有限值的處理。

## 3. 下一階段是否值得做與具體參數

**值得做的是「淘汰式品質 gate」，不是繼續最佳化，也不是三小時內證明無損。**若產品不能接受批次依賴，或沒有足夠的 ≥5-stream 生產負載，現在就應停止；dossier 尚無生產流量分布支持整體投資報酬。

以下為**建議測試方案**；沿用既有 `4:48:5`，不擴展 cap 32 或其他參數搜尋。修競爭後先重做既有 replay、no-op 與 off-path 檢查。

**三小時 GPU 時間上限，分成三個一小時區塊；到時停止，不以超時換取「pass」。**

| 區塊 | 具體安排 | 主要產物 |
|---|---|---|
| 配對答案測試 | 30 題、temp 0、seed 42，A/B 強制 C8；加入既有題庫中的長推理題。每題安排 8 個共同排程情境，最多每 arm 240 個目標答案【計算】 | 題目配對評分、退化案例、輸出分歧、實際觸發紀錄 |
| 工具與效能 | tool-eval-bench 配對同種子、loop probe；完整 C8 執行以各 arm 至少 5 reps 為目標，平衡 AB／BA 次序 | 工具成功率、迴圈、C8 吞吐／acceptance、每請求延遲與長度 |
| 穩定性 | 修正後 B 的 1h marathon，維持 C8，混合長推理與工具工作負載 | NaN、hang、完成計數、輸出缺失、跨 rank 選擇一致性 |

時間內無法完成的項目應列為「證據不足」，不是降低樣本量後照樣驗收。

**不要只把同一題複製八份。**相同問題、相近生成狀態可能大量共享 experts，使 union 不超過 cap【推論】。應：

- 將目標題和其他不同題目／既有工具工作負載共同排程，輪換同批成員。
- 固定每組 A/B 的請求集合與提交方式；短請求完成後補位維持 C8。
- 另做診斷執行，記錄 live streams、`union>48` 次數、實際刪除 slots／experts 與 guaranteed union 超 cap 次數。
- **八條連線不等於八條 live streams，更不等於 budget 有改寫。**

品質與診斷可以有 instrumentation；正式吞吐測試仍應關閉 hooks。

**配對與統計單位：**

- 保存 A/B 完整答案、終止原因、長度、工具參數與成功結果；評分時隱藏 arm。
- 以題目為主要配對單位，共同排程情境視為同題的重複量測。240 份答案仍只有 30 個獨立題目，不能宣稱樣本數增加八倍。
- 報告「A 對 B 錯」與「A 錯 B 對」的案例，不只報總分。
- `/metrics` 使用同一測試區間的  
  `Δmtp_accepted_total / Δmtp_drafted_total`，不是 drafted／accepted。確認計數器作用域，避免把 TP ranks 重複計入，並排除其他請求。
- 沒有 teacher forcing，就**不要以生成後不同 token 位置的比較冒充 top-1 一致率或 KL**。輸出分歧是診斷資料，功能正確性才是品質門檻。

## 4. 驗收門檻與回退條件

**建議採雙層判定：S3 通過只代表值得有限後續驗證，不等於可全面部署。**以下數值沿用前次審查的門檻，並修正其適用方式。

**正確性硬門檻**

- 修正共享記憶體競爭；既有 replay／no-op tests 維持零 mismatch。
- 在 active 執行中驗證兩 rank 的 picks／weights 一致，而不只比較配置。
- 以殘值、NaN／Inf 緩衝測試確認 dropped slots 不讀取或傳播舊 `y`；共享 expert 不受改寫。
- 無 NaN、hang、缺列、completion counter 卡住；1h marathon 通過。
- env off 與不觸發 budget 的路徑重新驗證身分一致。全域旗標重設及不支援配置須有明確處置。

**品質門檻**

- 30 題至少 28/30，**只作煙霧測試**；同時列出全部新增錯誤。
- loop probe 零新增迴圈；新增嚴重工具誤用或長推理失敗須先停下調查。
- C8 acceptance 下降不超過 0.01；它是機制與效率護欄，不是品質替代品。
- tool-eval 配對分數差的信賴區間下界至少 −3 個百分點。若區間跨越門檻，結論是**無法排除不可接受退化**，不是「沒有顯著差異，因此通過」。
- 若三小時內無法得到足夠獨立題目，允許結論為「煙霧測試通過、非劣性未成立」，但不允許改稱無損。

**效能門檻**

- 修正後、關閉 hooks 的 C8 提升至少 +4%，並報告以完整 run／arm 為單位的變異；「高於兩倍標準差」只能當粗略護欄，不能替代配對分析。
- 若實得低於 +3%，或無法與 run-to-run 雜訊區分，停止這條路線。
- 單流、C2、C4 不應出現可重複的退步。即使 streams 門控不改寫，只要 `R>=5` 仍可能啟動 kernel 後才 return；「budget inactive」不代表零成本。
- 不只驗收 aggregate tok/s：同時檢查每請求延遲、完成長度與功能成功，避免用更短或錯誤的答案換取吞吐【推論】。

**立即回退／停止條件：**

任何資料競爭未解、TP 結果不一致、數值或完成性錯誤、品質護欄失敗、產品拒絕批次依賴，均不應繼續最佳化。若只是樣本不足，維持 production off，不推廣部署。回退應重啟並核對恢復的 binary／環境，不能假定移除 env 就會清除全域旗標及已擷取的 graph 狀態。

**最終判定：效能訊號已足以購買一次有限的品質調查；尚不足以購買上線資格。這個專案下一個關鍵產物應是 active-C8 的配對品質證據，而不是更快的選擇 kernel。**
